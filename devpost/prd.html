Carve-Out Tutor (working title)

Run a finished 3D asset store, then rebuild two pieces of it with a tutor that hints but never answers. Your lines of code end up running inside the working store.

Scope said: "The tutor carves out one piece… the learner writes code… the tutor asks a question."

Now we know: the piece is authentication, then cart behavior, in a 3D asset store. Hints show up whenever you ask and after failed tests. Weak explanations get two hints before the tutor explains. The ownership score counts lines of code.

The core journey

Click a step, or use the buttons. Red shows a failed test, which loops back to work. Green shows round 2, which loops back to a new task.

Features & acceptance criteria

States & edge cases

First openThe catalog appears, and the ownership score is 0%.
Piece carved outRun project keeps using the AI's version until the learner's code passes, so the store never breaks.
Piece passedIt's the learner's code for good and never reverts. If it causes a bug later, they come back and fix it.
Close and come backNothing starts fresh. Finished pieces, the %, the current round and in-progress code are all restored.
Empty or broken code submittedThe tests fail and show the error, a hint is offered, and nothing is swapped in.
Wrong store log-inAn error message appears and the visitor stays logged out.
Empty cartThe cart says it's empty, and checkout isn't available.
After round 2Both pieces are the learner's, the store works end to end, and the score shows the final share.

What's in, what's not

Building now
  • Tutor screens: catalog (one project plus coming soon), project page, and learning workspace.
  • The store: log-in, browsing, cart, fake checkout, on-page download link and profile, opened in its own tab.
  • The carve loop: carving, focused task, hints, tests and swap-in, and the understanding check with retries.
  • Two rounds: authentication, then cart behavior. Ownership score always visible.
Deferred from the POC
  • Download links by email: needs a mail service and credentials. The on-page link proves the flow.
  • Real payments: need a payment provider and don't help prove the learning.
  • Sign-ups and multiple users: it's a one-user showcase.
  • Real 3D files and viewers: pictures are enough.
  • A working "Bring your own idea": needs live project generation, so it's shown but disabled.
Possible later
  • A bigger catalog: about ten project types.
  • Bring your own idea, for real: a Devpost-style interview, then AI-built projects.
  • Many more rounds: until 40% or more, and eventually the core, is yours.
  • More: games, mobile apps, other languages and a terminal. Accounts and saved progress for learners worldwide.
Non-goals
  • Detecting outside AI tools: can't be enforced. The understanding check does that job.
  • Worldwide deployment: not needed to prove the loop.
  • A full IDE: no terminal and no editing outside the carved piece.
  • Live generation: the store is prepared ahead of time.
  • Reverting a passed piece: once it passes, it stays the learner's.
